# 文档处理与 OCR

Yuxi 把文档处理拆成两步：先把原文件保存到知识库，再根据文件类型和 OCR 配置生成 Markdown。知识库索引使用生成后的内容；附件解析只把结果写回当前 Workdir，不会创建知识库文件记录。

文件状态和存储归属见[知识库机制详解](../mechanisms/knowledge-base.md)，第一次上传文档见[创建并使用知识库](../intro/knowledge-base.md)。

## 支持的文件

知识库上传接口当前支持：

- 文本：`.txt`、`.md`、`.html`、`.htm`、`.json`、`.csv`；
- Office：`.docx`、`.pptx`、`.xls`、`.xlsx`；
- PDF：`.pdf`；
- 图片：`.jpg`、`.jpeg`、`.png`、`.bmp`、`.tiff`、`.tif`、`.webp`；
- ZIP：压缩包内必须包含 UTF-8 编码的 `.md` 文件。

Office 文件不走 OCR 引擎：系统用内置的 docling-slim 在本地把它们转成 Markdown（`.docx`、`.pptx`、`.xlsx`、`.xls` 都有对应解析后端，API 镜像已附带所需的 LibreOffice 组件）。选择 MinerU Official 引擎时，`.docx` 和 `.pptx` 也可以直接交给该云服务解析。其余类型中，图片文件必须使用 OCR 引擎；知识库 PDF 选择 `disable` 时直接提取原生文字，另行提取插图，并可选择图片模型单独生成插图说明。

ZIP 处理会优先使用名为 `full.md` 的 Markdown 文件，否则使用压缩包中找到的第一个 `.md` 文件，并把 `images/` 下的图片上传到知识库图片存储。压缩包内的绝对路径和 `..` 路径会被拒绝。

## 从 URL 导入网页

网页导入受白名单控制。设置 `YUXI_URL_WHITELIST` 后，系统才会抓取 URL，并把 HTML 转成 Markdown 进入同一套知识库处理流程：

```bash
YUXI_URL_WHITELIST=github.com,docs.example.com,*.wikipedia.org
```

列表以逗号分隔；配置的域名及其子域名可以通过校验，空列表表示关闭 URL 导入。抓取器的安全边界由本页拥有：DNS 解析到 loopback、私有网段或 link-local 地址时拒绝请求，并逐跳检查重定向目标，最多跟随 5 次重定向，只接受 HTML，响应体默认不超过 10 MB。DNS 解析失败目前会记录日志后继续请求，因此 URL 白名单和地址检查不能当作网络出口防火墙；生产环境还应在网络层限制出口。

## 选择 OCR 方案

| 引擎 | 运行位置 | 输出和适用场景 |
| --- | --- | --- |
| RapidOCR | 本地 CPU | 轻量图片/PDF 文字识别 |
| OXR | 免费 API 或自托管服务 | 结构化论文 PDF/图片，保留公式、表格与图片位置；可另选正文校对模型 |
| MinerU | 本地 GPU 服务 | 复杂 PDF、表格和版面分析，输出 Markdown |
| MinerU Official | MinerU 云服务 | 不在本机部署 GPU，使用官方解析服务 |
| PP-Structure-V3 | 本地 GPU 服务 | 表格、票据和版面解析 |
| DeepSeek OCR | SiliconFlow API | 使用 SiliconFlow 的 DeepSeek OCR 模型 |
| PaddleOCR-VL-1.6 | 百度 AI Studio 云服务 | 文档版面解析，输出 Markdown |
| PP-OCRv6 | 百度 AI Studio 云服务 | 基础 OCR，输出纯文本 |

系统内部引擎 ID 为 `oxr_ocr`、`rapid_ocr`、`mineru_ocr`、`mineru_official`、`pp_structure_v3_ocr`、`deepseek_ocr`、`paddleocr_vl_1_6` 和 `paddleocr_pp_ocrv6`。页面中的健康状态只表示配置或服务探测结果，真正解析时仍会验证凭证和接口。

## 在页面配置

管理员进入“设置 → OCR 配置”可以设置默认引擎，并配置自托管服务地址或云端凭证。知识库上传和附件解析时可以单独选择引擎；没有单独选择时，使用系统默认值。

配置字段的读取规则是：数据库中保存的非空值优先，数据库没有值时读取对应环境变量。保存为空会清除数据库值并回到环境变量。API 不会回显环境变量中的密钥；数据库凭证只显示脱敏预览。

### 原生文字、插图与正文校对

系统初始默认引擎为“不使用 OCR”；管理员保存的默认选择继续生效。该模式读取 PDF 原生文字及其位置，将可定位位图保留在正文相应阅读位置。它适合文字层正常、版面简单的材料；原生文字层仍会丢失公式、上下标、字体编码或矢量图信息，需要完整论文识别时可选择 OXR 等版面解析引擎。

OXR 使用结构化块生成正文，默认把同一区域原生文字作为第二候选进行比对。上传或重新解析 PDF 时可分别选择“插图解析模型”和“正文校对模型”：前者只生成独立图片解释，后者先按区域证据进行保守规则修复，再对登记的少量疑点选择文字或局部视觉复核；不全篇重写。两个模型均可留空；模型留空不阻止主解析，OXR 的可证明规则仍执行。系统默认模型用于未传字段的请求，显式清空字段表示本次不调用该模型。其他 OCR 引擎保持各自解析流程。

文件详情的“图片解析”展示原图、原文图注与模型说明，“校对结果”展示局部原图、修改前后、关键修订、未决项和解析诊断。模型接收局部原图及对应目标，返回绑定问题ID的片段补丁，程序验证后重建完整块；数值、符号、公式和化学表达的变化保留关键修订标记。模型结果可能有误，机器修订仍需结合原 PDF 复核。

下载 Markdown 仅包含论文正文、原图、原文图注及已接受的局部修订。图片解释、解析提示和校对报告保存在独立产物中。单图说明或局部校对未返回可验证结果时保留主解析正文并明确显示未完成；主解析失败、原图无法保留且无法定位、或产物保存失败会让文件进入解析错误状态。Markdown 读取失败时停止正文下载，已有分块仍可在 Chunks 中查看。

旧文件显示缺少独立解析产物时，可在文件操作中选择“重新解析”。该动作读取原文件、生成新产物，成功发布前清除旧分块、向量和图谱，再回到 parsed；之后需要重新入库。原文件缺失或文件正在处理时不提供重新解析。失败会保留旧正文指针并显示错误，重试成功时仍会清理旧索引。

临时聊天附件未提供知识库图片归属时，不调用默认插图/校对模型。不使用 OCR 的附件保留只读原生文本行为；OXR 附件将解析图内嵌在字符串结果中，避免引用未知知识库目录。

### 完整复核与模型并发

OXR 结果先经过保护区和证据约束的规则处理，包括适用的普通正文空白、局部错字、表示等价分流和有明确来源的结构处理。原生文字只作候选；数字、单位、上下标、希腊字母及单双三键的变化必须有可靠证据。无法证明的内容保留原文并列为未决，不按常识补写。

“设置 → OCR 配置”中的“文档模型请求并发数”默认为 2，只接受正整数。相同服务端点与模型的正文复核、独立插图和多文件/worker共同使用此额度。保存后的实际准入直接读取数据库已提交配置；降额让在途请求完成，后续请求排队。每个文档的本地工作线程数在阶段开始时读取；提高额度后新阶段可使用更多工作线程。实际并行速度还取决于模型服务。

正文没有180秒、6次或视觉3次的篇级截断；图片没有300秒或20次的篇级截断。PDF调用显式不设置单次模型请求时限，页面也没有单次超时配置。现有任务取消、worker与OXR主解析的控制保持原样。Redis共享准入不可用时明确报告未完成，不退化为无约束请求。

模型请求只携带相关原文、登记目标和必要原图，每个问题必须明确返回修复、无误或无法确认。程序在目标、快照、原文及证据校验通过后，把声明修复但实际未改的回执归一为无改动；文字候选仍冲突时保留未决。重试携带逐问题拒绝代码，校对记录保留最终真实原因。大段普通文字按稳定跨度拆请求，公式和保护结构不强拆；超过可安全分片范围的数学原子保留未决。程序核对目标、版本、原图区域和保护区后重建完整块，结果从blocks渲染，不让模型自由改写全文。

知识库正文与独立图片任务在同一数据库事务发布。图片解释随后只更新同正文版本的附属JSON，不改Markdown或索引。图片任务完成后关闭并重新打开文件详情读取结果。其他OCR、Office、ZIP和临时附件保持原有入口语义。

正文主识别结果与复核状态分别记录。`incomplete`表示复核技术失败或缺少回执，任务摘要单独记录`review_incomplete`数量并提示警告，自动入库跳过这些文件；主MD发布成功时保留解析成功，仍可下载核对。OCR或产物发布失败继续按主解析失败处理。`needs_review`表示仍有无法确认的内容；`completed`只表达本次登记检查处理完毕，不保证论文零误差。未选择正文模型时不调用模型，保留规则结果和未启用状态。

### Token和失败排查

`[pdf_model]`逐次记录阶段、批次、request_id、attempt、输入字符/图片字节、输入token、输出token、总token、排队与调用耗时。用量来自模型实际返回；文字、视觉和插图分别汇总。无效JSON/不接受的补丁也已消耗token，因此先计量再校验。服务没有返回完整用量时标unknown/partial，汇总仅为已知消耗。

本地成功结果缓存命中没有新模型请求，日志标request_sent=false、token_increment=0，不重复累计历史token；思考与供应商缓存token仅在返回时记录为子项，不再加到total。日志不输出论文正文、模型完整回复、图片base64、思考过程或凭据。并发或取消期间的未知远端执行不能被解释为零消耗。

同事skill的保护区、事务补丁和审计思路在本地实现；不执行其CLI，不把忽略科学符号的宽松摘句作为改写依据。原始快照、规则版本、接受补丁、未决与计量均在附属结果中，下载MD仍是论文图文。

## 配置各类引擎

### OXR

部署后的验证项目见[OXR 解析验收](oxr-validation-checklist.md)。

在“设置 → OCR 配置 → OXR”配置服务基地址，需要填写并保存 API Base URL，例如免费接口 `https://free-oxr.somark.cn/api/v1`，也可填写镜像 `https://free-oxr.somark.ai/api/v1`。地址没有内置默认值；数据库和 OXR_API_URI 均为空时显示“未配置”，不能提交解析。免费接口不需要部署 OXR 或填写 API Key；上传时原文件会发送到所填服务。免费服务的可用性、速率和额度由服务方维护，页面显示“已配置”只代表参数就绪，实际解析才验证服务。

部署开源 OXR 后，把基地址替换为该服务的地址，例如 `http://oxr:8000/v1`。系统在基地址后追加 `/parse/async` 和 `/parse/async_check`，自托管地址不要再重复添加 `/api` 或完整端点。API Key 为可选字段；也可在 API/worker 环境中设置 `OXR_API_URI`、`OXR_API_KEY`，读取顺序与其他 OCR 配置相同。

系统请求 Markdown 和结构化 JSON，图片使用 base64，公式使用 LaTeX，表格使用 HTML，化学结构优先保留原图。仅发送已核实的 `keep_header_footer=false` 开关，跨页残留由本地有依据的版面规则整理；服务已正确合并的内容保持原结构。官方免费服务与开源自托管部署可能运行不同版本，不能用一个版本的表现推断另一个版本的全部功能。接口契约见 [OXR 官方源码](https://github.com/SoMarkAI/OXR)。

解析使用异步提交与查询，在本文件恢复点保存远程任务编号；同一源文件和服务配置匹配时，重试可继续查询已有任务。取消停止本地查询、模型调用和结果发布，OXR 没有已确认的远端取消接口，远端任务可能继续运行。重新解析可改变服务地址或模型，但不会静默改用其他引擎。

### RapidOCR

RapidOCR 随 API/worker 安装，第一次实际解析时加载 ONNX 模型。默认模型目录由 `RAPIDOCR_MODEL_DIR` 指定；没有设置时使用容器缓存目录。它不需要单独启动服务，但首次解析可能需要下载模型。

### MinerU

开发 Compose 已提供 `mineru-api`，它属于 `all` profile，端口为 `30001`，解析端点是 `/file_parse`：

```bash
docker compose --profile all up -d --build mineru-api
```

API/worker 在 Compose 中默认使用 `MINERU_API_URI=http://mineru-api:30001`。如果显存不足导致 MinerU 启动失败，可以在 `docker-compose.yml` 的 `mineru-api.command` 中启用并调整：

```yaml
# --gpu-memory-utilization 0.5
```

该参数用于减小 vLLM KV cache；仍然不足时可以继续尝试 `0.4` 或更低值。模型下载和其余显存参数以 `docker/mineru.Dockerfile` 与 Compose 为准。解析超时可以用 `MINERU_TIMEOUT` 调整，或在单次处理参数中传入 `timeout_seconds`。

### MinerU Official

在[官方服务](https://mineru.net)申请 API Key，放入 API/worker 的环境：

```bash
MINERU_API_KEY=<your-mineru-api-key>
```

页面中配置也可以保存该凭证；生产环境优先使用环境变量。该服务会把文件发送到外部服务，请先确认数据合规和供应商条款。

### PP-Structure-V3

开发 Compose 的 `paddlex` 服务属于 `all` profile，默认在容器内的 `8080` 端口提供版面解析：

```bash
docker compose --profile all up -d --build paddlex
```

API/worker 默认使用 `PADDLEX_URI=http://paddlex:8080`。本地 GPU 和镜像构建要求以 Compose 为准。

### DeepSeek OCR

在“智能体 → 模型供应商”中启用 `siliconflow-cn` 并配置凭证。DeepSeek OCR 会复用该供应商的 API 地址和 API Key，不接受单独的 OCR 凭证配置。

### PaddleOCR API

在[百度 AI Studio Access Token 页面](https://aistudio.baidu.com/account/accessToken)获取 Access Token：

```bash
PADDLEOCR_API_TOKEN=<your-paddleocr-token>
PADDLEOCR_API_URL=https://paddleocr.aistudio-app.com/api/v2/ocr/jobs
```

`PADDLEOCR_API_URL` 可省略，默认使用上面的地址。`PaddleOCR-VL-1.6` 和 `PP-OCRv6` 共用这组配置；前者输出 Markdown，后者输出纯文本。

## 分块参数和配置快照

知识库的分块配置由两部分组成：`chunk_preset_id` 表示策略，`chunk_parser_config` 保存该策略的具体参数。文件级 `processing_params` 会保存本次使用的 `ocr_engine`、分块策略和参数快照；OCR 服务地址和凭证在执行时读取，不写入文件快照。

修改分块策略不会自动重写已经索引的文件。要让旧文件使用新策略，需要重新解析或重新入库，并在最后确认文件状态和检索结果。

`Paper（论文证据）` 按章节组织完整公式及定义、图片与图注、Markdown/HTML 表格与标题。文中明确给出样品名且只有一个处理条件来源时，结果块携带该条件的原文；存在多个候选时保留未关联提示，使用者需要核对。该规则不抽取实验卡片，也不验证科学结论。

自动跨段关联仅识别 `Sample A`、`Sample SX-1` 等单个大写字母或以大写字母/数字开头且含数字的明确标识。未命名、名称格式不明确或原文说明是另一个实验时保留原文，不自动补入其他段落的实验条件。

数字小节支持独立标题和 `2.1. Synthesis. 正文` 形式的同行标题，分块保留各自小节路径。相邻英文文字在同节、同一明确实验身份、前段未结束且后段以小写续接时保留为一个证据；原文及其多范围坐标保持可回查。该规则不跨图表重排阅读顺序。图注与图片的完整保留不等同于正文图号到图块的自动检索扩展；多式推导也不自动扩展为整套方法上下文。文末参考文献保留在 Markdown 中并排除于 Paper 检索块之外，正文中的引用标记保留，平台不因此读取被引用论文。

论文策略的长度参数使用近似 token 计数，作为同节完整证据的组合目标；独立段落可在目标范围内组合并保留段落换行。完整段落、公式或表格以及附加上下文超过目标时保留全文并提示超长，较长块会占用更多检索与回答上下文；内容超出索引字段容量时入库显式失败。严格分隔策略保留按分隔符切开的语义，留空默认按换行，不能保证公式和表格完整。

文件详情的 Chunks 视图可展开完整证据正文并查看来源。Paper 卡片通过上方标签展示章节，正文区域隐藏自动生成的论文名和章节前缀；检索正文保留这些上下文。Markdown 行号对应当前解析正文；PDF 页码仅在同次解析版面块可以唯一精确匹配时提供。当前指纹和来源坐标通过核对且具有原 PDF 的文件，在来源处提供“查看 PDF 第 N 页”，使用现有文件预览打开并定位；越界页码显示明确提示。旧块缺少来源或来源版本不匹配时显示未知，重新入库可生成新来源。不同策略的比较方式见[分块方案同题对照](chunking-comparison.md)。

## 图片访问

解析器生成的知识库图片保存在私有 `kb-images` bucket，通过带知识库权限校验的后端路径访问。不要把 MinIO 对象地址直接写成公开 URL，也不要为方便预览而开放整个 MinIO 管理端口。头像等公开图片使用 `/minio/public/...` 同源只读代理，二者边界不同。

文件详情的“下载 Markdown”通过当前登录会话读取文档中的知识库图片，并内嵌为 data URI，下载后不依赖站内相对图片路径。同一图片重复引用只读取一次；图片读取失败、返回非图片或空内容时停止下载并显示错误。外部图片 URL 保持原样，导出不会携带用户认证向外部站点取图。下载文档会实际携带图片内容，分享时按文档本身的权限要求处理；离线显示需要 Markdown 阅读器支持 data URI 图片。

## 文件限制与排查

PDF 正文校对和插图解析在 worker 日志中分别带 `[pdf_review]`、`[pdf_figures]` 标记，记录 task_id、file_id、文件名、阶段总量、每项开始/结束、模型调用尝试、错误类型、用量与耗时。出现“模型调用开始”但尚无对应结束时，表示该调用仍在等待返回；execution 中 queue_seconds 是跨 worker 共享模型准入等待时间，调用耗时包含模型服务端排队和推理，不能单独视作纯推理耗时。任务中心文件级百分比不代表已完成同等比例的校对项。日志不写入论文正文或 MD，也不输出候选原文、模型回复或凭据。

- 知识库和工作区单个上传文件最大 100 MB。
- 工作区一次最多上传 50 个文件；知识库批量处理使用任务和页面限制。
- Agent 的 `read_file` 直接读取 UTF-8 文本和图片；PDF、Office 或其他二进制文件先用 `ocr_parse_file` 生成 Markdown。
- OCR 服务不可用时，先在 OCR 配置页查看健康状态，再检查容器日志、API 地址和凭证。
- 解析完成不等于索引完成；回到知识库文件列表确认 `parsed` 或 `indexed`，再做检索验证。

详细变量和容器映射见 `.env.template`、`docker-compose.yml` 和 `docker-compose.prod.yml`。文档页面只保留影响操作的配置，避免与配置文件维护两份默认值。
