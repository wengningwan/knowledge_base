# Paper 只维护当前实现

状态：implemented
类型：simplification
Owner：backend/package/yuxi/knowledge/chunking/paper.py

## 问题

Paper 后端只存在一套算法，但每次规则修正都递增结果中的编号，预览也依赖编号格式。用户明确要求取消这些编号设定，只使用当前最终实现。已存分块是独立持久结果，仍需正常展示与定位，不能把标签变更当成已经重新分块。

## 决策

### 实现方案

[Paper 分块器](../../../../backend/package/yuxi/knowledge/chunking/paper.py)删除编号常量与 `chunker_version` 输出，使用固定 `chunk_preset_id: paper` 表示策略。入库分发继续直接调用当前唯一函数，不按历史编号选择算法，不增加版本配置。

[预览](../../../../web/src/utils/chunkPreview.js)按固定策略标记及章节前缀识别 Paper。没有策略标记的既有记录，只在具有非空 `evidence_ids` 和章节路径时按既有 Paper 结构展示，不读取或枚举历史编号；显式其他策略和普通文本保持原文。来源指纹、字符范围、行号与 PDF 页码检查保留。

已有数据库分块和导出不自动重写；重新入库才使用当前规则并生成固定策略标记。文档中的旧编号只在历史验证证据中说明当时材料，不构成当前配置或算法选择。

## 替代方案

把版本字段固定成某个数字仍保留版本概念和前端耦合。删除全部识别条件会把普通正文中相似的论文/章节文本误作预览前缀。批量修改旧标签不能证明旧结果已执行当前算法，且需要不必要的数据迁移。

## 后果

分块算法修改直接进入当前实现，不再通过编号区分。旧数据上的编号不会被解释成算法选择或最新结果证明；已有检索内容与来源继续保留，更新分块需重新入库。原文指纹只证明正文一致性，不能代替程序部署或结果核对。

## 验证

重新引入条件：只有用户明确要求可切换且确有独立消费者的多套实现时另行设计，普通规则修正不恢复版本机制。
